# 06 — UI design workflow (Figma → LVGL)

## The honest starting point

**There is no dependable Figma-to-LVGL code generator.** LVGL's own tooling is LVGL Editor (part of
LVGL Pro) and SquareLine Studio — neither imports a Figma file. Community Figma plugins that claim to
export LVGL code exist, but they emit generated C that is awkward to hand-maintain and that fights
you the moment you need dynamic behaviour, which a feeder UI has everywhere (live status, schedule
editing, confirmation states).

So this project uses Figma as **the visual specification**, and writes LVGL by hand against it. That
is a deliberate trade: more typing, but the code stays readable, matches LVGL 8 idioms, and can be
reviewed in a PR like anything else. If you later want generated code for a static screen, nothing
here prevents it — just do not make the build depend on a generator whose output nobody can read.

The single most valuable thing this workflow buys is **numeric agreement**: the designer's reading and
the firmware's reading of "16 px" are the *same* number, because both come from one token file.

## Figma file setup

Rules for the file, so that it stays a specification rather than an artwork:

1. **Frame size is the panel size, exactly.** 800 × 480, or 1024 × 600 if you have that panel variant.
   Confirm which by flashing the vendor colour-bar test — see
   [02-hardware-and-wiring.md](02-hardware-and-wiring.md#verify-first--before-you-wire-anything).
   No scaling, no "design at 2×". A frame that is 99% of the panel size produces a UI that is
   subtly wrong everywhere.
2. **One top-level frame per screen.** Named exactly as the screen is named in the firmware and in
   [../design/screens.md](../design/screens.md) — `Home`, `FeedNow`, `ScheduleEditor`. A screen whose
   Figma name differs from its code name is a screen nobody finds.
3. **No effects LVGL cannot render.** Drop shadows, blurs, gradients layered over gradients, and
   blend modes have no LVGL 8 equivalent on this panel. Encode depth with colour and 1 px borders
   instead. Check this *before* the review, not after.
4. **Text in the actual font at the actual size.** Do not use a placeholder font and adjust later —
   character widths are the main reason a Figma layout does not fit once it is real text.
5. **Colour and spacing come from variables**, not from eyedropped hex values. This is what makes the
   token table exportable. See *Tokens* below.
6. **Dev Mode on** while reviewing, so measurements are numbers rather than guesses.

## Tokens — Figma variables to C

Figma variables (Local Variables, in the file's Variables panel) are the source of truth. The
checked-in transcription lives in [../design/tokens.md](../design/tokens.md) — that file is what the
firmware reads, so if the two disagree, the Markdown file is what ships and Figma needs fixing.

The hand-written header looks like this:

```c
// apps/hmi/main/ui/ui_theme.h — generated by hand from design/tokens.md
#pragma once

#include "lvgl.h"

// Colour. Panel is RGB565; LVGL quantises on assignment.
#define SAQ_C_BG          lv_color_hex(0x0E1621)
#define SAQ_C_SURFACE     lv_color_hex(0x1B2735)
#define SAQ_C_PRIMARY     lv_color_hex(0x2E9BD6)
#define SAQ_C_TEXT        lv_color_hex(0xF2F6FA)
#define SAQ_C_TEXT_MUTED  lv_color_hex(0x93A4B8)
#define SAQ_C_OK          lv_color_hex(0x3FB950)
#define SAQ_C_WARN        lv_color_hex(0xD29922)
#define SAQ_C_DANGER      lv_color_hex(0xF85149)

// Spacing scale — 4 px base
#define SAQ_SP_XS   4
#define SAQ_SP_SM   8
#define SAQ_SP_MD   16
#define SAQ_SP_LG   24
#define SAQ_SP_XL   32

// Radii
#define SAQ_R_SM    4
#define SAQ_R_MD    8
#define SAQ_R_PILL  20

// Minimum touch target. Below this, taps miss.
#define SAQ_TOUCH_MIN 44
```

Naming: Figma variable `colour/primary` becomes `SAQ_C_PRIMARY`; `space/md` becomes `SAQ_SP_MD`. Keep
the mapping mechanical so a reviewer can check it by eye.

**Do not** define these in `.c` files scattered across screens. One header, one place to change, and
a grep for a hex literal outside `ui_theme.h` should return nothing. That constraint is the whole
point of having tokens.

### Colour and the panel

The panel is 16-bit RGB565. `lv_color_hex(0xRRGGBB)` is fine and readable — LVGL quantises to 565 on
assignment. Two consequences to design around:

* **Bandwidth:** near-identical dark greys can collapse into the same 565 value and become invisible
  against each other. If two surfaces in a mockup are within a few 565 steps, one of them will vanish
  on the real panel. Test dark-on-dark contrast on hardware, not in Figma.
* **Anti-aliased text** on a gradient background looks noticeably rougher than the Figma render. Keep
  text on flat surfaces.

Check contrast numerically while designing — 4.5:1 for body text, 3:1 for large text and UI components.
Do not eyeball it; the panel is viewed from an arm's length in a room that may have a tank light
glaring off it.

## Screen inventory

Six screens. Each gets a section in [../design/screens.md](../design/screens.md) with layout, states,
and interactions, and a top-level Figma frame with the same name.

| Screen | Purpose | Key states |
| --- | --- | --- |
| `Home` | At-a-glance status: next feed, hopper, clock confidence, link | Normal / link-lost / clock-unsynced / fault |
| `FeedNow` | Manual feed with portion choice and confirmation | Idle / confirming / running / done / failed |
| `Schedule` | List of scheduled feeds | Empty / populated / editing |
| `ScheduleEditor` | Add or edit one entry: time, days, portion | New / edit / validation error |
| `History` | Recent feed log, reconciled from the node | Populated / empty / stale |
| `Settings` | WiFi, pairing, time, calibration, about | Idle / saving / error |

`Diagnostics` (link quality, uptime, raw status, clock confidence) is planned as a seventh, reachable
from `Settings`. It is the screen you will be glad exists when something is subtly wrong at 2 a.m.

## Component mapping

Sketch every Figma component against a real LVGL object *before* implementing. Discovering that a
design needs an object LVGL does not have is much cheaper than discovering it mid-implementation.

| Figma component | LVGL 8 object | Notes |
| --- | --- | --- |
| Button, primary | `lv_btn` + `lv_label` | Style for each state; `LV_STATE_PRESSED` / `DISABLED` |
| Button, danger (Feed) | `lv_btn` + `lv_label` | Distinct colour; always behind a confirmation |
| Card / surface | `lv_obj` with a style | `lv_obj_set_style_radius`, `border_width` 1 px |
| Text, heading / body / caption | `lv_label` | Three Montserrat sizes (16 / 20 / 24), already enabled |
| List row | `lv_obj` + `lv_label` | `lv_list` is awkward to style; a plain container row is easier |
| Toggle / switch | `lv_switch` | Style the indicator and knob separately |
| Slider (portion) | `lv_slider` | Set `lv_slider_set_range`; show the value in a label |
| Spinner (feed running) | `lv_spinner` | Use with a label; never leave a bare spinner |
| Progress arc | `lv_arc` | Good for "feed in progress" |
| Modal / confirmation | `lv_obj` overlay on the top layer | `lv_layer_top()`, plus a scrim behind |
| Toast | `lv_obj` on the top layer with a timer | Auto-dismiss; must not block input |
| Tab bar | `lv_obj` + buttons | Persistent chrome; keep it out of each screen's tree |
| Icon | `lv_img` from a C array | See *Icons* below |

## Layout conventions

* Grid: 12 columns, `SAQ_SP_MD` (16 px) gutters, `SAQ_SP_LG` (24 px) outer margins.
* Baseline spacing on the 4 px scale. Off-scale values in Figma are almost always a dragging accident.
* **Minimum touch target 44 × 44 px.** The GT911 is accurate, but a finger is not a cursor. Schedule
  list rows are the tempting place to go smaller — do not.
* Leave a **20 px dead margin** from every screen edge for primary actions. Capacitive panels are
  least accurate near the bezel, and this board's bezel is close to the active area.
* Persistent chrome (status bar and tab bar) is a fixed height so screens can be laid out knowing what
  space they have. Put the numbers in [../design/tokens.md](../design/tokens.md).
* Design for **landscape only.** Fixing rotation at 0° removes an entire class of layout bugs.

## Fonts

The vendor config already enables three Montserrat sizes in `sdkconfig.defaults`
([05-firmware-workflow.md](05-firmware-workflow.md)): 16, 20, 24. Start there — Montserrat is legible
and already costs you nothing.

To add a weight or size:

1. Generate it with the **LVGL font converter** (LVGL 8 tool, `lv_font_conv` / the web converter at
   `https://lvgl.io/tools/fontconverter`).
2. **Restrict the glyph range.** A full Latin font at 24 px with all symbols can run hundreds of KB of
   flash. Specify exactly the ranges you need: `0x20-0x7F` for ASCII, plus specific code points for
   `°`, `•`, and any arrows you use.
3. Output a `.c` file, drop it in `apps/hmi/main/ui/fonts/`, and add it to the app's `CMakeLists.txt`.
4. Declare it with `LV_FONT_DECLARE(my_font_20);` and set it in the style.

Choose the font **before** designing, and design with it in Figma. Swapping a font after screens are
laid out changes every wrap point in the UI.

## Icons and images

* Convert with the **LVGL image converter** to a C array: `LV_IMG_CF_TRUE_COLOR_ALPHA` for icons that
  need transparency, `LV_IMG_CF_TRUE_COLOR` for opaque images. Both work at `LV_COLOR_DEPTH` 16.
* Generate **at 1× the size you will display.** This is a 4.3" 800 × 480 panel; a 1024 px icon is
  wasted flash.
* Size matters more than it looks: an RGB565+alpha icon at 48 × 48 is roughly 4.6 KB of flash. That is
  fine. A **full-screen** 800 × 480 RGB565 background image is about **750 KB** — put images that large
  in PSRAM, or avoid them. Flat colour backgrounds cost nothing and look cleaner on this panel anyway.
* Keep the source SVG in `design/` (it is text, it diffs, it is small) and the generated `.c` in the
  app. Never commit PNG exports of icons.
* Prefer a small, consistent icon set. Mixing icon styles reads as unfinished more than any other
  single thing.

## Handoff checklist

Run through this before calling a screen ready to implement.

- [ ] Frame is exactly the panel size, landscape, 1:1 px
- [ ] Frame name matches the screen name in code and in `design/screens.md`
- [ ] Every colour traces to a Figma variable, and that variable exists in `design/tokens.md`
- [ ] Every spacing value is on the 4 px scale
- [ ] No shadows, blurs, or blend modes that LVGL 8 cannot render
- [ ] Real font, real size, real text — not lorem ipsum at a wrong size
- [ ] All interactive elements are ≥ 44 × 44 px
- [ ] Every state is designed: default, pressed, disabled, loading, **empty**, and **error**
- [ ] Screen-edge margin ≥ 20 px for anything tappable
- [ ] Contrast checked numerically (4.5:1 body, 3:1 large/UI)
- [ ] `design/screens.md` has a spec section for it: layout, states, interactions, LVGL notes
- [ ] The panel-size question is settled (800 × 480 vs 1024 × 600) — not guessed

The empty and error states are the ones that get skipped and the ones that matter. What does
`History` look like before anything has ever been fed? What does `Home` look like when the feeder node
is unreachable? Design those, or they will be improvised in code with no thought at all.

## Implementing a screen

Order of work, per screen:

1. **Read the spec** in `design/screens.md` and open the Figma frame in Dev Mode.
2. **Build static first.** All objects, correct positions, correct styles, no logic. Get it pixel-right
   against the frame.
3. **Add state handling.** One function per state transition, so the states are visible in the code
   rather than scattered through callbacks.
4. **Add interaction.** Wire callbacks to the app's event interface — screens talk to the app, not to
   the network directly.
5. **Screenshot on device and compare to Figma side by side.** Not from memory — actually put them next
   to each other. Colour and spacing errors that are glaring in a comparison are invisible when you
   look at the device alone.
6. **Only then** open a PR, with the on-device screenshot in the description.

### Working with the LVGL task

The vendor config runs `lv_timer_handler()` on its own task, on **core 1**. LVGL is **not
thread-safe**. Any code that touches an `lv_*` object from another task must hold the port's mutex:

```c
if (example_lvgl_lock(-1)) {
    lv_label_set_text(status_label, "Feeding…");
    example_lvgl_unlock();
}
```

Note the vendor's own typo: the helpers are spelled `example_lvgl_lock` / `example_lvgl_unlock` in
`ESP-IDF/08_lvgl_Porting/main/lvgl_port.h`, while the LCD helpers are misspelled
`wavesahre_rgb_lcd_bl_on` / `wavesahre_rgb_lcd_bl_off` in `waveshare_rgb_lcd_port.h`. That misspelling
is in the vendor source — do not "fix" it in your own calls unless you rename the whole file
consistently, and do not assume a helper is missing just because a grep for `waveshare_` came up
empty. Two rules prevent most crashes in a UI like this:

* Never touch an LVGL object from an ESP-NOW callback or a timer callback directly — take the lock.
* Never block while holding the lock. Do not do network I/O, NVS writes, or motor waits inside one;
  take the lock, change the widget, release, and do the work outside.

A hung LVGL task freezes the whole UI with the screen showing whatever was last drawn, which on a
feeder means the user cannot press Stop. Keep the locked sections tiny.
